The hygiene values contradict the settings WCMesh has published

High

[[P]] Phase 3: "Use flood advert 47h+, zero-hop 4h, set loop.detect minimal, and unique two-byte key prefixes." [[@plan:§04]]

What the sources show

  • [[F]] WCMesh's recommended repeater settings are set path.hash.mode 1, set txdelay 1.6, set direct.txdelay 0.8, set loop.detect moderate, set flood.advert.interval 47 ("Higher the better"), set advert.interval 0 ("Turns off direct adverts") and set owner.info. [[@wc-radio:L18-28]]
  • [[F]] On zero-hop adverts the Q1 report says: "Direct adverts I would keep at 0, since the parameter is set to minutes, even the max 240 is too much airtime." [[@wc-q1:L42]] The setup guide repeats the recommendation of 0. [[@wc-setup:L78]]
  • [[F]] On loop detection the Q2 report says: "I would suggest setting loop.detect to moderate as we move to 2 byte mode." [[@wc-q2:L63]]
  • [[F]] The plan's two differing values match the Netherlands guide: zero-hop adverts at 240 minutes and set loop.detect minimal. [[@nl-guide:L62-67, L129]] The PNW guide also uses minimal. [[@pnw-rollout:L175]]
  • [[F]] What the two modes do: under minimal a repeater drops a flood once its own hash already appears 4 times in a one-byte path, 2 times in a two-byte path or once in a three-byte path. Under moderate the thresholds are 2, 1 and 1. [[@fw-rep:L396-411]]
  • [[F]] 61.6 percent of the paths the analyzer counted in the week use one-byte hashes, and its per-repeater tally reads 263 one-byte against 445 two-byte and 70 three-byte. [[@cs-hash]]
  • [[F]] The firmware itself switches zero-hop adverts off the first time a setting is saved, if the interval is below 60 minutes. The comment reads "turn it off, now that device has been manually configured". [[@fw-cli:L160-166]]
  • [[F]] The plan omits the two transmit-delay settings WCMesh lists, owner.info, and flood.max.advert. [[@wc-q2:L95-100]]

Why it matters

[[I]] Both loop settings are defensible. With one-byte hashes and about 800 repeaters sharing 256 values, moderate will discard some legitimate long paths that happen to pass two repeaters sharing its prefix; minimal tolerates more real loops. WCMesh made that call and published it. A SoCal plan that silently carries the Dutch values asks operators to undo the local standard. [[I]] If you applied the four commands we went through on 10 October, SkyNet already runs the WCMesh values, and Phase 3 as written would move your own repeater away from them. [[@own-telemetry]]

Correction

[[R]] Replace the hygiene sentence with: "Apply the WCMesh recommended repeater settings as published. This plan changes none of them." Then list them verbatim:

WCMesh recommended repeater settings (firmware 1.14 or newer)
set path.hash.mode 1
set txdelay 1.6
set direct.txdelay 0.8
set loop.detect moderate
set flood.advert.interval 47
set advert.interval 0
set owner.info <how to reach you>

[[R]] If the plan wants minimal while one-byte paths are still the majority, it should say so as a proposed change to the WCMesh standard and argue it with the hash-size data.

9

The plan does not answer the maintainer's published position, or the tunneling threat he describes

High

[[P]] The plan cites the Q2 State of the Mesh five times, always for a number. [[@plan:§01, §05, RT-22]] It never mentions that report's Region/Scope section.

What that section says

  • [[F]] Q1: "There has been some talk about setting regions, however, I don't think it works with our mesh right now." [[@wc-q1:L84]]
  • [[F]] Q2: "Since we are on our own frequency, we pretty much have a built in region setting." and "Personally, I would like to keep things local and not implement bridges." [[@wc-q2:L78]]
  • [[F]] Q2: "We could add regions to our repeaters if we want to really define our mesh. There still is no way of decoding scopes in the companion software so everyone will still see every message, even if it is scoped." [[@wc-q2:L80]]
  • [[F]] The report opens by saying it is "not a definitive stance of the mesh" and that "Not a single person can police the mesh." [[@wc-q2:L12]]
  • [[F]] It describes a "tunneling event in PNW where someone is taking Bay Area traffic and injecting it into PNW", through what it calls a ghost repeater fed from MQTT data. [[@wc-q2:L84]]

Why it matters

[[I]] This is the first objection the plan will meet, from the maintainer whose account also committed the competing SoCal names (Finding 1). He is right on the main point: the perimeter argument for scoping is already met by frequency. The case that survives is narrower. Scoping in SoCal can only help by containing automated and local floods inside one mesh, and the plan has to make that case with numbers (Finding 3).

[[F]] On tunneling, public region names protect nothing. A region's key is the first 16 bytes of SHA-256 of # plus the name, and the code on a packet is an HMAC over the payload type and payload alone. [[@fw-regionmap:L175-183; fw-tks:L4-18, L44-47]] [[I]] Nothing in that input depends on time, sender or location, so a replayed scoped packet carries a valid code wherever its name is allowed. [[F]] Private regions, the names starting with $, have no working key storage: the save routine is a TODO that returns failure. [[@fw-tks:L52-76]] [[F]] A repeater remembers only its 160 most recent packet hashes for duplicate detection. [[@fw-tables:L9]] [[I]] A packet replayed after that window looks new. Denying the wildcard or capping unscoped hops stops replayed unscoped traffic only.

Correction

[[R]] Add a short section titled "Response to the Q2 State of the Mesh" with four points: (1) agreed, frequency already gives SoCal its outer boundary, and this plan proposes no bridges; (2) the proposal is about floods inside SoCal, two thirds of which by message count are test, bot and wardriving traffic; (3) companions do not filter on receive, so scoping changes who relays a message and does not hide it from anyone in range; (4) scoping is a traffic tool and offers no defense against replay.

Needs Discord. Whether this position has moved since July. The August commits to the generator suggest it has.

10

The wide scope saves nothing inside an isolated mesh, replies follow the replier, and no gate is measurable

High

[[P]] Companions set Default Region Scope to socal; Public, #socal and the emergency channels go to socal. [[@plan:§03, §05]] [[P]] Phase 4 starts at boundary nodes with "either region denyf * or the gentler set flood.max.unscoped 3". [[@plan:§04]] [[P]] "Success means the unscoped share trends down while scoped delivery remains intact." [[@plan:§04]]

What the sources show

  • [[F]] Once a packet's region resolves, the forwarding checks are the same for scoped and unscoped floods, apart from the separate unscoped hop limit. [[@fw-rep:L434-458; fw-routing:L15-22]] [[I]] If every SoCal repeater carries socal and nothing outside SoCal shares the frequency, a socal-scoped flood is relayed by exactly the repeaters that relay an unscoped one. The airtime saving is zero.
  • [[F]] A scoped flood is 4 bytes longer than an unscoped one, because the two 16-bit codes are written into the packet. [[@fw-packet:L52-58]] [[C]] At this preset that is about 10 milliseconds, or 4 percent, on the mesh's average 56-byte packet. [[@own-toa; cs-rf]] [[I]] Moving traffic to socal without any change in who relays it therefore raises airtime slightly.
  • [[C]] Requests, direct messages, anonymous requests, path returns, responses and ACKs add up to 37 percent of relay airtime. [[@cs-airtime]] [[I]] Under the plan all of that moves to socal through the companion default, together with Public. The plan's own success metric can therefore reach 100 percent scoped with no reduction in load.
  • [[F]] The metric's denominator includes direct-routed packets, which never carry a transport code, so the unscoped share cannot approach zero either. [[@cs-src-db:L3288-3299]]
  • [[F]] A companion's ACKs and path returns go out under the replier's own setting: unscoped if the app asked for that, otherwise the app's current scope override, otherwise the replier's default scope. [[@fw-chat:L252-302; fw-comp:L500-510]] [[F]] Canada's guide says it in user terms: "The reply that tells your companion the path comes back using your contact's default scope." [[@ca-onqc:L768-769]]
  • [[F]] A repeater's own replies use the request's scope when it can resolve it, go unscoped when the request was unscoped, and fall back to its default scope otherwise. [[@fw-routing:L60-66; fw-rep:L413-431]]
  • [[F]] The median observed path in SoCal is 9 hops and the mean 11.1. [[@cs-topo]] [[I]] A 3-hop limit on unscoped floods is therefore close to a denial for anything that needs to cross the region. "Gentler" overstates the difference.
  • [[P]] The only condition on companions is "only after the repeaters serving them carry the relevant tags". [[@plan:§04]] [[I]] Nobody can test that sentence.

Why it matters

[[I]] During migration a scoped user and an unscoped user can reach each other only while both socal and the wildcard are forwarded along the whole path. The day boundary nodes deny the wildcard or cap it at 3 hops, replies from every companion that has not migrated die at the boundary, and the migrated sender sees messages that are never acknowledged. Emergency channels have the same exposure: while the wildcard is allowed everywhere, unscoped is the widest reach there is, and scoping an emergency channel can only shrink it.

Correction

[[R]] Say plainly that socal is plumbing for a later strict phase and saves no airtime by itself. Keep emergency and alert channels unscoped until a wide-scope test message reaches every observer site. Replace Phase 4's two options with a staged limit that starts high and steps down only on evidence. Replace the success sentence with outcome measures. Each of these is written out in Corrected rollout and Measures that can fail.
