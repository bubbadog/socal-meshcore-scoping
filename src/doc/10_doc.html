01 · Summary

The short version

SoCal's mesh is busy enough that its own maintainer says it is starting to hit the range where messages get lost. This document proposes an order of work that reduces that load, and it lists what is still unknown.

about 2,850channel messages a day last week, roughly double the Q2 average of 1,332
68%of decodable channel messages are test, bot or wardriving traffic
4different sets of SoCal region names exist, and scoped traffic already uses two of them
0 of 30audited repeaters declare a named region today

Sources and caveats for each figure are in Why now and Names.

What this suggests

  1. Start with settings that need no agreement. The WCMesh repeater settings, advert limits, a hop-limit trial and quieter bots. Rollout, step 1.
  2. Agree one set of region names before anyone tags a repeater. The people who maintain the WCMesh docs, the config generator and MeshMapper each already have a list. Names.
  3. Tag repeaters first, and leave their default scope alone until neighbors are tagged too. Otherwise the first repeater to move stops being heard beyond one hop. How scoping works.
  4. Scope machines before people. One MeshMapper setting and a few bot owners control most of the channel traffic. Channels.
  5. Measure airtime and delivery at every step, and stop when a step does not help. Measures.

What has to happen before the research is complete

  1. Someone inside the WCMesh Discord reads the history. Neither assistant could get in, so nothing here reflects what the community has already discussed.
  2. The maintainers of the three tools say which names they intend.
  3. Airtime is measured at several repeaters, so the load picture rests on more than one site.
  4. Two pilots run: one to prove the mechanism, one to show whether load falls.
  5. People who know the network check this page. Every claim has a source so that it can be checked.

The full list, with who can do each item, is in Research still needed.

02 · A note from the author

Why I wrote this, and what I do not know

I am new to this technology. I have my repeater, SkyNet, set up in Thousand Oaks, and I am still learning how the network works.

I put this together because I would like the mesh to be useful, robust and efficient for everyone, and I think a little planning can help with that. I hope it can be a small contribution to a project that a lot of people have already put real work into.

I am not trying to step on anyone's toes. The people who built and run this network know far more about it than I do, and some of what follows is probably wrong or already decided somewhere I have not looked. If so, please tell me. That is what the feedback section and the open repository are for.

04 · Why now

The mesh is close to the load its maintainer warned about

[[F]] The Q2 2026 State of the Mesh says: "We are starting to hit that 20%-25% threshold before the mesh starts getting overwhelmed." [[@wc-q2:L39]] [[F]] The Q1 report defines the quantity: "Around 20% airtime utilization is the limit of when packets start to break down." [[@wc-q1:L22]] [[C]] The analyzer counted about 2,850 channel messages a day in the week to 13 October, against a Q2 average of 1,332. [[@cs-rf; wc-q2:L37]] [[U]] The two counts may not use the same method, so read that as "roughly double".

[[E]] At one repeater in the Conejo Valley, the radio's own counters for a 46-minute window on the afternoon of 10 October imply the channel was occupied about 22 percent of the time. [[@own-telemetry]] That is one site at a busy hour, and the all-day figure there is probably nearer 14 percent.

[[E]] Channel messages are 44.5 percent of relay airtime and 68.4 percent of them are test, bot or wardriving traffic, so that traffic is about 30 percent of all relay airtime, if airtime per message is similar across channels. Confining it to a metro that holds 30 percent of the repeaters would save roughly a fifth of all relay airtime. [[E]] County and city channels are about 1.1 percent of relay airtime on the same assumption. That is the most that scoping those channels could save.

05 · How scoping works

Regions live on repeaters. Scopes travel with floods.

[[F]] A region is a name in a repeater's table. A scope is a 16-bit code a sender puts on a flood packet, computed from a region name and the packet's own bytes. A repeater forwards a scoped flood only when the code matches a name it holds with flooding allowed. Each name is tested independently and a parent is never consulted. [[@fw-regionmap:L190-204; fw-tks:L4-18]] [[F]] A flood with no code matches the wildcard *, which every repeater allows out of the box. Packets sent along a known path are not scope-checked. [[@fw-regionmap:L46-49; fw-rep:L434-443, L556-568]]

The trap for whoever goes first

[[F]] A repeater sends its own flood adverts under its default scope. [[@fw-rep:L1031-1038, L1294-1297]] [[I]] So the first repeater in a neighborhood to set a default scope has its adverts dropped by every neighbor that lacks the name. [[F]] The SoCal air shows the pattern: three scoped adverts from one Coachella Valley repeater were each recorded after a single relay and no further, while an unscoped advert from SkyNet was recorded 64 times over paths up to 11 hops. [[@cs-packets; own-decode; cs-advert]] [[I]] The one repeater that relayed them either holds psp too or runs firmware too old to filter. Either way the adverts stopped where the name stopped.

Two more facts that shape a rollout

  • [[F]] A companion's replies go out under the replier's own scope setting, so a scoped user and an unscoped user can talk only while both kinds of flood are forwarded along the whole path. [[@fw-chat:L252-302; fw-comp:L500-510; ca-onqc:L768-769]]
  • [[F]] Names are case-sensitive on repeaters, and the published rule is lower case, at most 29 bytes, letters, digits and hyphen. [[@fw-regionmap:L52-55, L207-216; blog-region]]

06 · Names

Four sets of names already exist. Pick one before tagging anything.

[[F]] The WCMesh docs carried a SoCal region list for about 22 hours in March 2026, inside a regions section that lasted about 55 hours. [[@wc-regions-old:L7-28; wc-log]] [[F]] The account that owns the WCMesh docs committed a second list, with counties and 52 local areas, to the matkam config generator on 3 and 24 August 2026. [[@mk-c1; mk-c2; mk-data:L112-118, L945]] [[F]] MeshMapper divides SoCal into five zones with airport codes. [[@mm-socal]] [[F]] Drafts v3 to v5 of this plan proposed a fourth list. [[@plan5:§05]]

[[F]] Scoped packets already on the air carry psp, san and california, each matched on three or more packets. [[U]] One more packet matches us; that rests on a single match and is probable, not certain. [[@own-decode]] [[I]] That is two names from the airport family and at least one from the generator's chain. [[I]] Because matching is per name, a repeater set up from one list and a radio set up from another can meet only on a name both lists contain. Drafts v3 to v5, the generator and the wiki draft all contain socal, and the generator and the wiki draft both contain us. No metro or county name appears in more than one of those three lists.

[[O]] Three ways to converge, each with a cost. A. Adopt the generator's tree as it stands. The maintainer wrote it and a tool already emits it. A Conejo repeater then carries six names, three of which (us, west, california) do nothing inside an isolated SoCal, and today's psp and san users re-tag. B. Adopt the airport metros of drafts v3 to v5 and have the generator and wiki changed. This asks the maintainer to reverse the August work. C. A short flat set: socal, one metro name per MeshMapper zone, and the generator's area names for local tags. This reuses each existing vocabulary at the layer where a tool already emits it and keeps a repeater to three entries. It has one flaw to solve first: san is the beginning of generator area names such as santaclarita and sanjacintovalley, which breaks the prefix rule below, so the San Diego metro would need another name. [[@mk-data:L945-1326]] This draft leans to C, with low confidence. Whichever is chosen, the choice belongs to the people who maintain the three tools.

Naming rules, whichever set is chosen

  • [[F]] Lower case, at most 29 bytes, letters, digits and hyphen. [[@blog-region]]
  • [[R]] No name may be the beginning of another name. [[F]] The CLI's allowf, denyf, get and default match by prefix when no exact name exists. [[@fw-regionmap:L218-231]] This rules out pairs such as oxr with oxr-conejo, which earlier drafts used, and san with santaclarita.
  • [[R]] A published name is never renamed. [[F]] "any misspellings will be treated as a completely different region". [[@blog-region]]
  • [[R]] Names stay flat. [[F]] Nesting does not change forwarding. [[@pnw-rollout:L105]]

Repeater roles

  • [[R]] Metro repeater. Holds its metro name and socal. Most repeaters, including peaks that serve one metro.
  • [[R]] Wide-only site. Holds socal only. For a site whose measured job is to link metros.
  • [[R]] Overlap repeater. Holds two metro names and socal. [[I]] It gives people in the seam coverage under either metro's scope. It retransmits each metro's floods, so they are heard one hop into the other metro, and they stop there because a packet has one code and the next repeater along holds only its own metro's name. A chain of overlap repeaters would carry them further, so keep such sites few. [[@fw-rep:L997-1005; blog-region]]
  • [[R]] Local tag. A name for a community that sits across a metro line, held by the repeaters that serve it. [[F]] The PNW plan uses the same device. [[@pnw-rollout:L113]]

Why the analyzer's region tags are weak evidence for any list

07 · Answer to the Q2 report

What the State of the Mesh already said about regions

[[F]] The Q2 report says "Since we are on our own frequency, we pretty much have a built in region setting", prefers "to keep things local and not implement bridges", and notes that "There still is no way of decoding scopes in the companion software so everyone will still see every message, even if it is scoped." [[@wc-q2:L78-80]] This plan accepts all three points.

  1. [[I]] Frequency already gives SoCal its outer boundary. This plan proposes no bridges and no shared root with any other mesh.
  2. [[I]] The proposal is about floods inside SoCal. A wide socal scope changes nothing about who relays a message inside an isolated mesh, and it adds 4 bytes to each flood. [[@fw-packet:L52-58]] The saving comes only from scopes smaller than the whole mesh, applied to the traffic that is large.
  3. [[F]] Scoping changes who relays a message. It hides nothing. Companions do not filter on receive. [[@wc-q2:L80; blog-region]]
  4. [[I]] Scoping would not stop the tunneling the report describes. [[F]] The report describes someone "taking Bay Area traffic and injecting it into PNW". [[@wc-q2:L84]] [[F]] A region's key is derived from its public name and a packet's code from the packet's own bytes, and private regions have no working key storage. [[@fw-tks:L4-18, L44-47, L52-76]] [[I]] So anyone who knows a region's name can stamp a valid code on injected traffic. Strict forwarding would drop injected traffic that carries no code, and nothing more.

[[F]] The report presents itself as one view: it is "not a definitive stance of the mesh". [[@wc-q2:L12]] [[F]] Its suggestion to limit bots to acknowledgements is worded as a proposal, ending "Can discuss further." [[@wc-q2:L39]]

08 · Rollout

Six steps, each with a test that can fail

[[O]] The thresholds below are starting proposals. [[I]] No community this plan looked at has published results for scoping inside a single isolated mesh. Scotland denied unscoped floods first, under pressure from a neighbor on its frequency. The Netherlands makes strict forwarding a required last step. Canada's proposal is experimental. The PNW plan has no dates. [[@scot-regions:L15, L66-74; nl-guide:L42, L157-164; ca-onqc:L8-12; pnw-rollout:L5-10]]

  1. 1
    Now: settings that need no agreement. [[R]] Apply the WCMesh repeater settings as published. Ask bot owners to consider acknowledgement-only behavior, as the Q2 report suggests. Check that get flood.max.advert returns 8 or less on 1.16 and newer. Design a hop-limit trial. [[@wc-radio:L18-28; wc-q2:L39; fw-rep:L907]]TestAirtime at reference repeaters, before and after.
  2. 2
    Decide and measure. [[R]] One set of names agreed with the three tool maintainers. A firmware census. Baseline counters from at least five repeaters in different metros. The agreed names loaded into the analyzer so scoped traffic becomes visible. [[@cs-src-cfg:L400-404]]GateAll four exist in writing.
  3. 3
    Tags only. [[R]] Repeater owners add the metro name and socal with flooding allowed. No default scope. The wildcard stays allowed.Gate, per metro[[O]] A message scoped to the metro, sent from one edge, is heard at every observer in that metro on three separate days.
  4. 4
    Default scope on repeaters. [[R]] region default <metro>, only in metros that passed the gate.TestEach repeater's next flood advert still reaches an observer.
  5. 5
    Machines, then people. [[R]] The MeshMapper administrator sets the Wardriving Scope for that zone, and bot owners set the bot radio's default scope to the metro. [[@mm-admin; blog-default]] Later, people may scope local channels, and companion default scope moves to socal. Emergency and alert channels stay unscoped until the gate for people is passed, then move to socal so that step 6 cannot cut them off.Gates[[O]] For machines: MeshMapper coverage unchanged week over week and relays per flood down. For people: a socal-scoped message reaches every observer site and at least 95 percent of repeaters hold socal.
  6. 6
    Containment, optional. [[R]] On 1.16 and newer, step flood.max.unscoped down from 12, holding each value for 30 days. Consider region denyf * only by agreement across the whole mesh. [[F]] The Dutch guide warns that it "only works reliably from v1.15 onwards". [[@nl-guide:L56]]Gate[[O]] Unscoped share of flood-routed channel messages under 5 percent for 30 days.

Region commands

[[F]] Five rules first. (1) Names are lower case, at most 29 bytes, letters, digits and hyphen. [[@blog-region]] (2) No name may be the beginning of another name, because the CLI matches by prefix. [[@fw-regionmap:L218-231]] (3) Before any allowf, denyf or default, run region get <name> and check that the reply echoes exactly the name you meant. [[@fw-cli:L1086-1097]] (4) region default saves everything at once and invents a region from a typo. [[@fw-cli:L1109-1128]] (5) [[R]] Work over USB or from direct radio range, and confirm you can still log in before you leave.

[[F]] region def answers with the resulting tree. Each region get should answer with the name followed by F, meaning flooding is allowed. [[@fw-cli:L1041-1057, L1086-1097]]

[[F]] Each region put answers "OK - (flood allowed)". [[@fw-v115:L971-981]]

3. Tags only, firmware 1.12 to 1.14. Upgrade instead if the site can be reached.

[[F]] On these versions a new region starts denied, and there is no default scope. [[@fw-v1141:L1234-1245; blog-default]] [[F]] Version 1.11 only matches names that begin with #; the requirement was dropped in 1.12. [[@fw-v111:L123-134; blog-region]]

4. Other roles, firmware 1.16 or newer. Run one line, then region save.

The first line is a wide-only backbone site. The second is an overlap repeater on the Ventura and Santa Barbara seam.

5. Default scope, rollout step 4 only, firmware 1.15 or newer.
region get oxr
region default oxr
advert

[[F]] The reply must read "default scope is now oxr". It saves immediately. advert sends a flood advert at once so you can check it still reaches an observer. Undo with region default <null>. [[@fw-cli:L195-197, L1109-1128]]

6. Rollout step 6, option A: limit unscoped hops. Firmware 1.16 or newer. Never combine with block 7.
set flood.max.unscoped 12
get flood.max.unscoped

[[F]] Saved on entry; no region save needed. Undo with set flood.max.unscoped 64. A value of 0 has the same effect as denying the wildcard. [[@fw-cli:L632-639; fw-routing:L19; ca-onqc:L617]]

7. Rollout step 6, option B: strict forwarding. Firmware 1.15 or newer, by mesh-wide agreement only.
region denyf *
region save

[[F]] Undo with region allowf * then region save. [[@pnw-rollout:L241]]

8. Remove a name added by mistake. The name must be exact and must have no children.
region remove oxr-typo
region save

11 · Pilots

Two pilots, because they answer different questions

Pilot A, mechanics, Conejo Valley.

  1. Partners. At least three contiguous repeaters: SkyNet, one neighbor toward Los Angeles, and NP-CAM Grade, which carried SkyNet's advert to the Camarillo observer in one hop. [[@cs-advert]] Ask the analyzer's maintainer to load the test names first.
  2. Instrument. On-node counters on each pilot repeater, read before and after: flood packets received and sent, duplicates, receive errors, transmit and receive airtime. [[@fw-stats:L28-50; fw-rep:L232-233; own-telemetry]] The analyzer is the secondary check.
  3. Configure. Tags only, using the block for each node's firmware. No default scope yet.
  4. Test 1, positive control. Send a message scoped to the pilot tag from one end of the cell. Pass: a companion at the other end, two hops away, receives it.
  5. Test 2, negative control. The same message must not be received by a companion one hop outside the cell, and the analyzer must show no path that leaves the pilot nodes. If it leaks: suspect a pre-1.10 repeater and record which one. [[@blog-region]]
  6. Test 3, unscoped control. An unscoped message sent in the same minute still arrives outside the cell.
  7. Test 4, the app and capitals. Type the scope in mixed case in the app and repeat Test 1. This is the case test that matters.
  8. Test 5, default scope. Set the default on one pilot node, send advert, and count the observations the analyzer records against the 64 it recorded for SkyNet's unscoped advert on 11 October. [[@cs-advert]] Prediction: far fewer, possibly none.

Appendix

Reading the scopes already on air

[[F]] The firmware derives a region's key as the first 16 bytes of SHA-256 over # plus the name, and a packet's code as the first two bytes of HMAC-SHA256 under that key over one byte of payload type followed by the payload, with the values 0x0000 and 0xFFFF moved to their neighbors. [[@fw-regionmap:L175-183; fw-tks:L4-18, L44-47]] [[F]] The analyzer serves the raw bytes of scoped packets and marks them as scoped with no resolved name. [[@cs-packets; cs-src-db:L3270-3278]] [[F]] Of 13 such packets from 11 to 13 October, 12 match a name: three flood adverts from one Coachella Valley repeater match psp; three Public messages from one user match san; four posts from a bot match california; two messages from another user match us and california. [[@own-decode]] [[F]] Twelve of the 13 came from the analyzer's latest 58 transport-route packets and one was fetched separately. [[@cs-packets]] [[C]] A single packet has about a 7 percent chance of matching some name among the 4,461 tried by accident; the same name matching three packets from one sender does not happen by accident. The lone us match is therefore probable, not certain.

Python 3, standard library only. Returns the code a packet would carry under a given name.
import hashlib, hmac

def code(name, raw_hex):
    b = bytes.fromhex(raw_hex)
    ptype = (b[0] >> 2) & 0x0F               # payload type from the header byte
    n = b[5]                                 # path length byte, after two 16-bit codes
    path = ((n >> 6) + 1) * (n & 0x3F)       # hash size times hop count
    payload = b[6 + path:]
    key = hashlib.sha256(('#' + name).encode()).digest()[:16]
    mac = hmac.new(key, bytes([ptype]) + payload, hashlib.sha256).digest()
    return mac[:2].hex().upper()             # compare with raw_hex[2:6]

# The firmware also moves the reserved codes 0000 and FFFF to a neighbor.
# tools/decode_scope.py in the repository handles that case.
