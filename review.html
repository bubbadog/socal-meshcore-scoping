It reviews working draft 3 (an internal draft; the published edition is public draft 1) and is published unchanged for transparency, except that the names of individual users and of three audited repeaters are withheld. Errata. A later independent check of Draft v6 found six errors that this review also carries. They are corrected in Draft v6 and left as written here.

  1. Command block 0: on firmware older than 1.16, get flood.max.unscoped and get flood.max.advert answer with the plain flood.max value. They do not answer with an error, so they do not reveal the firmware generation.
  2. Namespace option C does not avoid prefix names: san is the beginning of generator area names such as santaclarita.
  3. The generator has declared no tags since 24 August 2026. On 3 August only socal stopped being a tag.
  4. "About 22 hours" is the life of the SoCal region list. The regions section that held it lasted about 55 hours.
  5. The three psp adverts were each relayed once, so one other repeater either holds psp or runs firmware too old to filter.
  6. County and city channels are about 1.1 percent of relay airtime, where this page says 1.2. The us scope rests on a single packet and is probable, not certain.

The plan describes the mechanism correctly and draws the wrong strategy from it. Its account of how regions and scopes behave matches the firmware source nearly line for line. The problems are in what it does with that mechanism and in what it says about the mesh it is written for. Four of them should stop this draft from going to the community as it stands.

  1. It forks the namespace. The plan proposes airport-code metros. The account that owns the WCMesh docs committed a different SoCal tree (counties and local areas) to the matkam generator in August 2026, and the plan describes that scheme from a stale README. Two further vocabularies exist. Scoped traffic using both families of names is already on the air. Finding 1.
  2. It calls the load modest. The report it cites for its numbers says the mesh is starting to hit the 20 to 25 percent threshold. Live channel traffic is about twice the figure the plan quotes, and SkyNet's own counters put its late-afternoon channel occupancy near 22 percent. Finding 2.
  3. It aims at the smallest traffic. The design effort (24 sub-regions and a terrain map) serves local channels that carry 2.6 percent of channel messages. Wardriving pings (24 percent) have no policy at all, and test and bot traffic (about 45 percent) gets one line in a late phase. Finding 3.
  4. Its first step is not purely additive. region default <metro> scopes a repeater's own flood adverts, and every neighbor without that tag drops them. The single-node pilot cannot detect this, or anything else the plan wants it to prove. Findings 4 and 5.

The rest is repairable in an edit pass: wrong or misattributed citations, hygiene values that contradict the WCMesh published settings, a terrain table with three rows on the wrong side of a mountain range, and a cookbook that only works on one firmware generation. 1

The plan forks a namespace that is already forked, and misdescribes the competing scheme

Critical

Plan says The metro tier is airport codes (lax, lgb, sna, ont, san, oxr, sba, psp), sub-regions are <metro>-<place>, and the wide tag is socal. [1 §03, §05] Plan says The matkam California scheme appears in the reference list as "Alternative considered", and the plan says choosing socal "aligns with the alternative matkam California scheme's existing tag concept". [1 §05, §10, RT-12]

What the sources show

  • Fact The generator's data file declares no tags (tags: []). Its comment says SoCal communities live as areas under each county. [35 L127-130]
  • Fact In that file socal is a level under the root chain us, west, california. Beneath it are eight counties (santabarbara, ventura, losangeles, orangecounty, sanbernardino, riverside, imperial, sandiego) and 52 local areas. Thousand Oaks is an alias of conejovalley under ventura. [35 L112-118, L945, L992-1021]
  • Fact The SoCal section was rewritten by the GitHub account chrisdavis2110 in two commits, on 3 and 24 August 2026. [37; 38] Fact That account owns the WCMesh documentation repository, which publishes the State of the Mesh reports. [25]
  • Fact The generator's README still describes socal as a tag and says Ventura County is split at the Conejo grade because its east half talks to Los Angeles. [36 L297-298, L328-345] Inference The plan's alignment claim was written from that README. The data that drives the generator stopped matching it on 3 August.
  • Fact WCMesh's own docs carried a third scheme for about 22 hours: us, ca, socal, then la, oc, sd, ie, sb, vta. It was added late on 3 March 2026 and removed on the evening of 4 March with the two-word message "removed regions"; the removal deleted the whole guide, 25 files. [31 L7-28; 34; 33] Fact The guide's explainer page used lax, oc and socal as its example names. [32 L16-22]
  • Fact Nothing about regions has entered the WCMesh docs since the Q2 report: the five commits after 26 July add that report, a settings table and MQTT notes. [33] Inference So the August commits to the generator are the only public statement of SoCal region names by that maintainer since the March guide was withdrawn. A search limited to the WCMesh docs repository will miss them, and the second assistant's memo did. [85]
  • Fact MeshMapper's SoCal map lists five zone codes under "Wardriving Scope": LAX, OXR, PSP, SAN and SBA. [65]
  • Fact Scoped traffic already exists on the SoCal air under both families of names. Of 13 scoped packets I decoded from 11 to 13 October: all three flood adverts from the repeater Rancho North, which sits in the Coachella Valley at 33.80, -116.40, carry psp; three Public messages from one user carry san; four #weather posts from a bot carry california; two messages from another user carry us and california. One packet matched no name I tried. [82; 59; 60]
  • Fact The analyzer cannot show any of this. It reports every scoped packet as an unknown scope and an empty per-region list, which is what its source says happens when no region names are configured for matching. [48; 63 L400-404]

Why it matters

Fact A repeater forwards a scoped flood only if the packet's code matches one of the names in its own table; the loop compares each name's code in turn and never consults a parent. [3 L190-204] Inference So a repeater set up from the generator and a companion set up from this plan share one working scope, socal. Every metro or local scope from either vocabulary is dropped by repeaters that hold the other.

Inference Names get adopted through tool defaults. Three parties control those defaults here: whoever maintains the WCMesh wiki and analyzer, the MeshMapper administrator for SoCal, and the generator's maintainer. A plan that is not wired into those three becomes the fifth vocabulary.

Opinion Airport codes are a defensible choice. They match five of MeshMapper's zones, the PNW and Canadian conventions, and two of the scopes already on air. [39 L241-248; 44 L66] The county and area tree is also defensible: it has 52 named SoCal areas with aliases and a working generator. The failure is presenting one as the proposal and the other as a footnote, without the other's author in the room.

Correction

Recommendation Replace the "Ratify the airport-code metro tier?" decision with a convergence step that happens before any repeater is touched: one thread with the WCMesh docs and analyzer maintainer, the MeshMapper SoCal administrator and matkam, one written vocabulary as its output, and the same names loaded into the generator, MeshMapper's Wardriving Scope and the analyzer's hashRegions list on the same day. The crosswalk table below is the working paper for that thread.

Recommendation Replace the sentence about matkam in §05 with: "A second SoCal vocabulary already exists in the matkam generator: socal as a level under us, west, california, with eight county names and 52 local-area names, committed in August 2026 by the WCMesh docs maintainer. It shares only the name socal with this plan. The two must be reconciled before rollout."

Needs Discord. Whether WCMesh has already chosen between these, why the March guide was pulled, and who runs Rancho North and the bot posting under california.

2

"Healthy" and "modest load" contradict the plan's own source and the live data

Critical

Plan says The opening reads "The network is healthy" and "Scoping is not a rescue operation", and the rollout can proceed "while load is still modest". [1 §01] Plan says The same section quotes "20 to 25%" as the community's Q2 estimate of the overwhelm threshold and "1,332/day" as the channel-message total. [1 §01]

What the sources show

  • Fact The sentence the 20 to 25 percent figure comes from is: "We are starting to hit that 20%-25% threshold before the mesh starts getting overwhelmed." The author continues, "I would like to keep the mesh healthy and not have it crumble." [25 L39]
  • Fact The quantity is airtime utilization. The Q1 report says "Around 20% airtime utilization is the limit of when packets start to break down" and that the mesh was "mostly hovering around 10%". [26 L22]
  • Fact 1,332 per day is the April to June average. [25 L37] Fact The analyzer recorded 19,919 channel-message transmissions in the 168 hours to 13 October. [50] Calculation That is 2,846 per day, 2.1 times the Q2 average. Unverified I could not confirm the two counts use the same method, so read the ratio as "roughly double", not as a measured growth rate.
  • Fact SkyNet's own counters for a 46-minute window on 10 October (about 4:30 to 5:16 pm PDT): 1,603 flood packets received, 1,279 of them duplicates; 316 floods sent; about 99 seconds of transmit time; 249 receive errors on about 1,890 decode attempts. Its lifetime totals at the start of that window were 58 minutes of transmit airtime and 4 hours 46 minutes of receive airtime. [81]
  • Estimate Channel occupancy at SkyNet in that window was about 22 percent. Two independent routes agree: 1,603 received floods at the measured 0.313 seconds per packet is 502 seconds (18.2 percent) plus 3.6 percent transmit; or the lifetime receive-to-transmit airtime ratio of 4.93 applied to the 99 seconds of transmit gives 17.7 percent plus 3.6 percent. Assumptions: received packets average the same airtime as sent ones, and packets that failed to decode are not counted, which makes this a floor. Working in Appendix C.
  • Estimate That window is a late-afternoon peak. SkyNet saw about 423 unique floods per hour in it, against a seven-day network mean of about 275 per hour, so the all-day average at this site is probably nearer 14 percent. [52]
  • Calculation 80 percent of the floods SkyNet received in that window were duplicates, and 13.2 percent of decode attempts failed. [81]

Why it matters

Inference The evidence supports "approaching the threshold the maintainer named, at peak hours, at one site in the Conejo Valley". It does not support "healthy" or "modest". The framing sets the sequencing: a plan that believes there is no pressure defers the cheap volume levers (bots, wardriving, advert and hop limits) to Phase 3 and leads with a naming exercise.

Fact One correction of my own. On 10 October I told you SkyNet was "healthy and lightly loaded". [81] Inference I based that on its 3.6 percent transmit duty cycle alone. Transmit time measures what one repeater adds; it says little about how full the channel is. The same counters, read for receive airtime, give the 22 percent above.

Correction

Recommendation Replace the §01 headline and first tile row with the corrected baseline below, and replace the two sentences with: "The Q2 2026 State of the Mesh says SoCal is starting to hit the 20 to 25 percent airtime range where the mesh gets overwhelmed. Channel traffic in the week to 13 October ran at about twice the Q2 average. The first job is to cut flood volume with settings that need no fleet-wide agreement. Scoping comes after that."

Recommendation Measure occupancy directly instead of estimating it. Fact The firmware keeps both counters, the repeater's status screen in the app shows them (your 10 October screenshots did), and the serial command stats-radio returns them as tx_air_secs and rx_air_secs. [81; 14 L28; 15 L148-150] Recommendation Read them twice, 24 hours apart, and divide the change in their sum by 86,400. Fact The receive counter adds the estimated airtime of every packet the radio parses, duplicates included. [12 L204-209]

Needs Discord. Any airtime measurements or a Q3 report posted after July.

3

The design effort is inverted relative to where the traffic is

Critical

Plan says The plan defines 24 candidate sub-regions across eight metros and a terrain section to justify them. [1 §06] Plan says Its channel table has rows for region-wide, emergency, metro, neighborhood and "Test / bot" channels, and no row for #wardriving. [1 §05] Plan says Bots are addressed in Phase 3 of five: "Curtail bots through acknowledgement-only behavior and metro-scoped bot channels." [1 §04] Plan says RT-22 removed the bot-share figure because the Q2 report's categories do not sum to its total. [1 RT-22]

What follows from the two charts

  • Calculation Test, bot and wardriving channels are 68.4 percent of channel messages (13,338 of 19,487). Local channels, the traffic sub-regions exist to contain, are 2.6 percent. [54]
  • Estimate Channel messages are 44.5 percent of relay airtime, so automated and test traffic is about 30 percent of all relay airtime and local-channel traffic about 1.2 percent, if airtime per message is similar across channels. Confining the automated traffic to a metro that holds 30 percent of the repeaters would save roughly a fifth of all relay airtime. Perfect sub-region scoping of every local channel could not save more than 1.2 percent.
  • Fact Wardriving has a single control point. MeshMapper's admin setting "Wardriving Scope" is "The scope the app puts on every Active and Hybrid ping", with the warning "Repeaters not set up for it drop those pings." [67] Fact The app sends each ping as a channel message to #wardriving, and "If your regional admin has configured a scope, the message stays within that region instead." [68] Fact Each of SoCal's five zones showed the value #* when I looked. [65] Inference I read that as the wildcard, meaning no scope is set yet. Unverified The second assistant's memo reports the MeshMapper leaderboard showing "Wardriving Scope: not set" for all five; my own fetch of that page did not reach those columns. [85; 66]
  • Fact Adverts are 18 percent of relay airtime. [51] Fact The firmware already caps advert floods at 8 hops by default from 1.16, and the Q2 report suggests stretching flood adverts toward 72 to 96 hours. [6 L907; 25 L35, L55]
  • Fact The maintainer's stated view is "I for one think there are too many bots", with a proposal to limit them to acknowledgement-only. [25 L39]
  • Fact The bot share the plan deleted in RT-22 can be measured directly: the analyzer publishes a message count per channel. [54] Calculation The Q2 categories do overshoot the total (335 + 601 + 504 = 1,440 against 1,332), and so do the Q1 figures (304 + 485 + 416 = 1,205 against 1,162), so RT-22 was right about the report and wrong to stop there. [25 L37; 26 L44]

Correction

Recommendation Reorder the plan around volume. Machines first, people later: (1) hop and advert limits and the WCMesh hygiene settings, now; (2) repeater tags; (3) MeshMapper's Wardriving Scope per zone and bot owners' default scope, as each metro's repeaters are ready; (4) human channels; (5) sub-regions only where a local group asks for one. Canada's proposal sequences bots and MeshMapper the same way, at the end of its repeater phase and before companions. [39 L342-344] The full sequence with gates is in Corrected rollout, and the channel table with message counts is in Corrected channel table.

Recommendation Cut §06 to a half page. Keep the rule that measured RF decides, keep a corrected barrier table as background, and move the 24 candidate names to an appendix labeled "not proposed for adoption".

Needs Discord. Who administers MeshMapper for SoCal, who owns the active bots, and whether ack-only bots were ever agreed.

4

Phase 1 is not purely additive: a default scope blacks out the first mover's adverts

High

Plan says Phase 1 tells operators to "add tags with region def, set region default, save" and to "Keep * allowed". [1 §04] Plan says Role A says a metro repeater's "default is the metro, so its own adverts remain local". [1 §03] Plan says The pilot configuration for SkyNet ends with region default oxr. [1 §07]

What the sources show

  • Fact A repeater sends its flood adverts with its default scope, both on the timer and on demand. [6 L1031-1038, L1294-1297]
  • Fact A receiving repeater sets the packet's region to the first allowed name whose code matches, or to nothing. With nothing, it refuses to forward: the debug text reads "unknown transport code, or wildcard not allowed for FLOOD packet". [6 L434-443, L556-568]
  • Fact Keeping * allowed does not help. The wildcard only matches floods that carry no transport code at all. [6 L559-564]
  • Fact Observed on the SoCal air: Rancho North's psp-scoped adverts each reached the analyzer over exactly one hop, by way of one repeater (prefix F420). [59; 82] Fact SkyNet's unscoped advert of 11 October was observed 64 times, over paths up to 11 hops long. [58]
  • Fact The PNW guide the plan follows states the assumption out loud: "Your neighbors carry that tag, so your adverts still reach them". [44 L129] Fact The firmware author's own advice for repeater default scope is that it "should typically be a large region". [22]

Why it matters

Inference The first repeater in any neighborhood to run region default oxr will have its flood adverts forwarded by nobody. Direct neighbors still hear it. Everything beyond one hop stops refreshing it, including the analyzer unless an observer is in direct range. For SkyNet that is a testable prediction: its 11 October advert reached the nearest observer through NP-CAM Grade, one hop away, so after the pilot command its flood adverts should stop appearing on CoreScope. [58]

Inference The harm is moderate. Messaging does not depend on repeater adverts, and the Q2 report says adverts "aren't really necessary on the mesh". [25 L35] The problem is that the plan promises operators that Phase 1 cannot hurt them, and the first ones to follow it will watch their node go stale on the map.

Correction

Recommendation Split Phase 1. In 1a, add tags and save; leave the default scope unset. In 1b, set the default only after a contiguity gate for that metro is met. Replace Role A's sentence with: "Once most of its neighbors carry the metro tag, its default becomes the metro, so its own adverts stay local. Until then it has no default and its adverts flood unscoped as before." Remove region default oxr from the pilot block until at least the repeaters between SkyNet and one observer carry oxr.

5

The pilot's success criteria cannot fail, and a single low-traffic node cannot show the benefit

High

Plan says The pilot configures SkyNet alone and lists four criteria: the three tags appear in Discover Regions; a message scoped oxr-conejo "is forwarded by SkyNet"; the test "stays out of adjacent metros when spot-checked in CoreScope packet data"; unscoped traffic still flows. [1 §07] Plan says It describes SkyNet with "454 relays in 24 hours", "18 hops average relayed packet path", "0.0% bridge score" and a neighbor list that ends with "Hyperion Fatline · 60.8 mi". [1 §07]

What the sources show

  • Inference Criterion three passes whether or not scoping works as designed. No other repeater carries oxr-conejo, so the message cannot travel past SkyNet's direct neighbors under any outcome.
  • Fact There is one way it could fail, and it is unrelated to the design: repeaters older than 1.10 forward scoped floods without checking them. The firmware author wrote that with such repeaters in an area "scoped flood packets will leak into other regions". [21]
  • Fact CoreScope would display the test packets as unknown scope until the instance is given the names. [48; 63 L400-404]
  • Fact The analyzer's own usefulness score for SkyNet is 0.10, which it grades F, with traffic share 0.05, redundancy 0 and bridge score 0. [57] Inference The plan reads a zero bridge score as "clean test case". It also means almost no observed traffic depends on this node, so a pilot anchored on it will carry very few scoped packets.
  • Fact "454 relays in 24 hours" is the analyzer's count (452 when I fetched it). [57] Fact SkyNet's own counter shows 316 floods sent in 46 minutes. [81] Inference The analyzer only sees relays that end up in a path recorded by an observer, so it undercounts this node's work by more than a factor of ten. Analyzer relay counts are the wrong instrument for a before-and-after test.
  • Fact "18 hops" is not stable. The node's seven-day hop analytics on 13 October showed 61 packets, an average of 9.28 hops, a median of 9, and 4,043 packets set aside as ambiguous. [57]
  • Fact SkyNet's second most-observed neighbor, "Highest in the Neighbor" (160 of 737 observations, behind NP Valley Spare with 209), is at 34.274, -118.792. [57; 61] Calculation That is about 1 km from the generator's reference point for Simi Valley (34.269, -118.781) and about 12 km from its point for the Conejo Valley (34.17, -118.838). [35 L1016-1027] Inference One of the two busiest links of the proposed "clean Conejo Valley test case" crosses the Simi Hills, the very line the plan draws between oxr-conejo and oxr-simi. A pilot cell drawn from the terrain table would cut it.
  • Fact The Hyperion Fatline link rests on 120 observations that all fall inside a ten-second window on 8 October, resolved from the one-byte prefix 80, at 97.9 km. [57] Inference That pattern is a prefix collision resolved to the wrong node, and the entry should come out of the neighbor list.
  • Fact The data does support the Ventura-side affiliation. SkyNet's advert reached an OXR-tagged observer in Camarillo in one hop through NP-CAM Grade (prefix 8943). The shortest path to any LAX-tagged observer was four hops. [58] Inference Observer placement shapes those counts, so treat this as supporting evidence. It also answers a disagreement inside the generator repository, whose README puts east Ventura County with Los Angeles while its data now puts the Conejo Valley under Ventura. [36 L297-298; 35 L1016-1021]

Correction

Recommendation Replace §07's criteria with the pilot protocol below: at least three contiguous repeaters including the Conejo Grade site, on-node counters as the instrument, a positive and a negative control, and a stated prediction for each test. Say plainly that a mechanics pilot cannot show load reduction. A second, separate pilot that scopes one high-volume automated source for one zone can.

Needs Discord. The owners of NP-CAM Grade, RASN, Green R1, NP Valley Spare, NP 700 ASL and COMT, who are the pilot's necessary partners.

6

The hygiene values contradict the settings WCMesh has published

High

Plan says Phase 3: "Use flood advert 47h+, zero-hop 4h, set loop.detect minimal, and unique two-byte key prefixes." [1 §04]

What the sources show

  • Fact WCMesh's recommended repeater settings are set path.hash.mode 1, set txdelay 1.6, set direct.txdelay 0.8, set loop.detect moderate, set flood.advert.interval 47 ("Higher the better"), set advert.interval 0 ("Turns off direct adverts") and set owner.info. [27 L18-28]
  • Fact On zero-hop adverts the Q1 report says: "Direct adverts I would keep at 0, since the parameter is set to minutes, even the max 240 is too much airtime." [26 L42] The setup guide repeats the recommendation of 0. [28 L78]
  • Fact On loop detection the Q2 report says: "I would suggest setting loop.detect to moderate as we move to 2 byte mode." [25 L63]
  • Fact The plan's two differing values match the Netherlands guide: zero-hop adverts at 240 minutes and set loop.detect minimal. [42 L62-67, L129] The PNW guide also uses minimal. [44 L175]
  • Fact What the two modes do: under minimal a repeater drops a flood once its own hash already appears 4 times in a one-byte path, 2 times in a two-byte path or once in a three-byte path. Under moderate the thresholds are 2, 1 and 1. [6 L396-411]
  • Fact 61.6 percent of the paths the analyzer counted in the week use one-byte hashes, and its per-repeater tally reads 263 one-byte against 445 two-byte and 70 three-byte. [56]
  • Fact The firmware itself switches zero-hop adverts off the first time a setting is saved, if the interval is below 60 minutes. The comment reads "turn it off, now that device has been manually configured". [7 L160-166]
  • Fact The plan omits the two transmit-delay settings WCMesh lists, owner.info, and flood.max.advert. [25 L95-100]

Why it matters

Inference Both loop settings are defensible. With one-byte hashes and about 800 repeaters sharing 256 values, moderate will discard some legitimate long paths that happen to pass two repeaters sharing its prefix; minimal tolerates more real loops. WCMesh made that call and published it. A SoCal plan that silently carries the Dutch values asks operators to undo the local standard. Inference If you applied the four commands we went through on 10 October, SkyNet already runs the WCMesh values, and Phase 3 as written would move your own repeater away from them. [81]

Correction

Recommendation Replace the hygiene sentence with: "Apply the WCMesh recommended repeater settings as published. This plan changes none of them." Then list them verbatim:

WCMesh recommended repeater settings (firmware 1.14 or newer)
set path.hash.mode 1
set txdelay 1.6
set direct.txdelay 0.8
set loop.detect moderate
set flood.advert.interval 47
set advert.interval 0
set owner.info <how to reach you>

Recommendation If the plan wants minimal while one-byte paths are still the majority, it should say so as a proposed change to the WCMesh standard and argue it with the hash-size data.

Python 3, standard library only
import hashlib, hmac

def code(name, raw_hex):
    b = bytes.fromhex(raw_hex)
    ptype = (b[0] >> 2) & 0x0F               # payload type from the header byte
    n = b[5]                                 # path length byte, after two 16-bit codes
    path = ((n >> 6) + 1) * (n & 0x3F)       # hash size times hop count
    payload = b[6 + path:]
    key = hashlib.sha256(('#' + name).encode()).digest()[:16]
    mac = hmac.new(key, bytes([ptype]) + payload, hashlib.sha256).digest()
    return mac[:2].hex().upper()
