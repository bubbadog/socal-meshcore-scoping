01 · Summary

The short version

SoCal's mesh is busy enough that its own maintainer says it is starting to hit the range where messages get lost. This document proposes an order of work that reduces that load, and it lists what is still unknown.

about 2,850channel messages a day last week, roughly double the Q2 average of 1,332
68%of decodable channel messages are test, bot or wardriving traffic
4different sets of SoCal region names exist, and scoped traffic already uses two of them
0 of 30audited repeaters declare a named region today

Sources and caveats for each figure are in Why now and Names.

What this suggests

  1. Start with settings that need no agreement. The WCMesh repeater settings, advert limits, a hop-limit trial and quieter bots. Rollout, step 1.
  2. Agree one set of region names before anyone tags a repeater. The people who maintain the WCMesh docs, the config generator and MeshMapper each already have a list. Names.
  3. Tag repeaters first, and leave their default scope alone until neighbors are tagged too. Otherwise the first repeater to move stops being heard beyond one hop. How scoping works.
  4. Scope machines before people. One MeshMapper setting and a few bot owners control most of the channel traffic. Channels.
  5. Measure airtime and delivery at every step, and stop when a step does not help. Measures.

What has to happen before the research is complete

  1. Someone inside the WCMesh Discord reads the history. Neither assistant could get in, so nothing here reflects what the community has already discussed.
  2. The maintainers of the three tools say which names they intend.
  3. Airtime is measured at several repeaters, so the load picture rests on more than one site.
  4. Two pilots run: one to prove the mechanism, one to show whether load falls.
  5. People who know the network check this page. Every claim has a source so that it can be checked.

The full list, with who can do each item, is in Research still needed.

02 · A note from the author

Why I wrote this, and what I do not know

I am new to this technology. I have my repeater, SkyNet, set up in Thousand Oaks, and I am still learning how the network works.

I put this together because I would like the mesh to be useful, robust and efficient for everyone, and I think a little planning can help with that. I hope it can be a small contribution to a project that a lot of people have already put real work into.

I am not trying to step on anyone's toes. The people who built and run this network know far more about it than I do, and some of what follows is probably wrong or already decided somewhere I have not looked. If so, please tell me. That is what the feedback section and the open repository are for.

04 · Why now

The mesh is close to the load its maintainer warned about

Fact The Q2 2026 State of the Mesh says: "We are starting to hit that 20%-25% threshold before the mesh starts getting overwhelmed." [20 L39] Fact The Q1 report defines the quantity: "Around 20% airtime utilization is the limit of when packets start to break down." [21 L22] Calculation The analyzer counted about 2,850 channel messages a day in the week to 13 October, against a Q2 average of 1,332. [39; 20 L37] Unverified The two counts may not use the same method, so read that as "roughly double".

Estimate At one repeater in the Conejo Valley, the radio's own counters for a 46-minute window on the afternoon of 10 October imply the channel was occupied about 22 percent of the time. [69] That is one site at a busy hour, and the all-day figure there is probably nearer 14 percent.

Estimate Channel messages are 44.5 percent of relay airtime and 68.4 percent of them are test, bot or wardriving traffic, so that traffic is about 30 percent of all relay airtime, if airtime per message is similar across channels. Confining it to a metro that holds 30 percent of the repeaters would save roughly a fifth of all relay airtime. Estimate County and city channels are about 1.1 percent of relay airtime on the same assumption. That is the most that scoping those channels could save.

05 · How scoping works

Regions live on repeaters. Scopes travel with floods.

Fact A region is a name in a repeater's table. A scope is a 16-bit code a sender puts on a flood packet, computed from a region name and the packet's own bytes. A repeater forwards a scoped flood only when the code matches a name it holds with flooding allowed. Each name is tested independently and a parent is never consulted. [3 L190-204; 4 L4-18] Fact A flood with no code matches the wildcard *, which every repeater allows out of the box. Packets sent along a known path are not scope-checked. [3 L46-49; 6 L434-443, L556-568]

The trap for whoever goes first

Fact A repeater sends its own flood adverts under its default scope. [6 L1031-1038, L1294-1297] Inference So the first repeater in a neighborhood to set a default scope has its adverts dropped by every neighbor that lacks the name. Fact The SoCal air shows the pattern: three scoped adverts from one Coachella Valley repeater were each recorded after a single relay and no further, while an unscoped advert from SkyNet was recorded 64 times over paths up to 11 hops. [48; 70; 47] Inference The one repeater that relayed them either holds psp too or runs firmware too old to filter. Either way the adverts stopped where the name stopped.

Two more facts that shape a rollout

  • Fact A companion's replies go out under the replier's own scope setting, so a scoped user and an unscoped user can talk only while both kinds of flood are forwarded along the whole path. [9 L252-302; 8 L500-510; 31 L768-769]
  • Fact Names are case-sensitive on repeaters, and the published rule is lower case, at most 29 bytes, letters, digits and hyphen. [3 L52-55, L207-216; 17]

06 · Names

Four sets of names already exist. Pick one before tagging anything.

Fact The WCMesh docs carried a SoCal region list for about 22 hours in March 2026, inside a regions section that lasted about 55 hours. [25 L7-28; 26] Fact The account that owns the WCMesh docs committed a second list, with counties and 52 local areas, to the matkam config generator on 3 and 24 August 2026. [29; 30; 27 L112-118, L945] Fact MeshMapper divides SoCal into five zones with airport codes. [55] Fact Working drafts 3 to 5 of this plan proposed a fourth list. [2 §05]

Fact Scoped packets already on the air carry psp, san and california, each matched on three or more packets. Unverified One more packet matches us; that rests on a single match and is probable, not certain. [70] Inference That is two names from the airport family and at least one from the generator's chain. Inference Because matching is per name, a repeater set up from one list and a radio set up from another can meet only on a name both lists contain. Working drafts 3 to 5, the generator and the wiki draft all contain socal, and the generator and the wiki draft both contain us. No metro or county name appears in more than one of those three lists.

Opinion Three ways to converge, each with a cost. A. Adopt the generator's tree as it stands. The maintainer wrote it and a tool already emits it. A Conejo repeater then carries six names, three of which (us, west, california) do nothing inside an isolated SoCal, and today's psp and san users re-tag. B. Adopt the airport metros of working drafts 3 to 5 and have the generator and wiki changed. This asks the maintainer to reverse the August work. C. A short flat set: socal, one metro name per MeshMapper zone, and the generator's area names for local tags. This reuses each existing vocabulary at the layer where a tool already emits it and keeps a repeater to three entries. It has one flaw to solve first: san is the beginning of generator area names such as santaclarita and sanjacintovalley, which breaks the prefix rule below, so the San Diego metro would need another name. [27 L945-1326] This draft leans to C, with low confidence. Whichever is chosen, the choice belongs to the people who maintain the three tools.

Naming rules, whichever set is chosen

  • Fact Lower case, at most 29 bytes, letters, digits and hyphen. [17]
  • Recommendation No name may be the beginning of another name. Fact The CLI's allowf, denyf, get and default match by prefix when no exact name exists. [3 L218-231] This rules out pairs such as oxr with oxr-conejo, which earlier drafts used, and san with santaclarita.
  • Recommendation A published name is never renamed. Fact "any misspellings will be treated as a completely different region". [17]
  • Recommendation Names stay flat. Fact Nesting does not change forwarding. [34 L105]

Repeater roles

  • Recommendation Metro repeater. Holds its metro name and socal. Most repeaters, including peaks that serve one metro.
  • Recommendation Wide-only site. Holds socal only. For a site whose measured job is to link metros.
  • Recommendation Overlap repeater. Holds two metro names and socal. Inference It gives people in the seam coverage under either metro's scope. It retransmits each metro's floods, so they are heard one hop into the other metro, and they stop there because a packet has one code and the next repeater along holds only its own metro's name. A chain of overlap repeaters would carry them further, so keep such sites few. [6 L997-1005; 17]
  • Recommendation Local tag. A name for a community that sits across a metro line, held by the repeaters that serve it. Fact The PNW plan uses the same device. [34 L113]

07 · Answer to the Q2 report

What the State of the Mesh already said about regions

Fact The Q2 report says "Since we are on our own frequency, we pretty much have a built in region setting", prefers "to keep things local and not implement bridges", and notes that "There still is no way of decoding scopes in the companion software so everyone will still see every message, even if it is scoped." [20 L78-80] This plan accepts all three points.

  1. Inference Frequency already gives SoCal its outer boundary. This plan proposes no bridges and no shared root with any other mesh.
  2. Inference The proposal is about floods inside SoCal. A wide socal scope changes nothing about who relays a message inside an isolated mesh, and it adds 4 bytes to each flood. [10 L52-58] The saving comes only from scopes smaller than the whole mesh, applied to the traffic that is large.
  3. Fact Scoping changes who relays a message. It hides nothing. Companions do not filter on receive. [20 L80; 17]
  4. Inference Scoping would not stop the tunneling the report describes. Fact The report describes someone "taking Bay Area traffic and injecting it into PNW". [20 L84] Fact A region's key is derived from its public name and a packet's code from the packet's own bytes, and private regions have no working key storage. [4 L4-18, L44-47, L52-76] Inference So anyone who knows a region's name can stamp a valid code on injected traffic. Strict forwarding would drop injected traffic that carries no code, and nothing more.

Fact The report presents itself as one view: it is "not a definitive stance of the mesh". [20 L12] Fact Its suggestion to limit bots to acknowledgements is worded as a proposal, ending "Can discuss further." [20 L39]

11 · Pilots

Two pilots, because they answer different questions

Pilot A, mechanics, Conejo Valley.

  1. Partners. At least three contiguous repeaters: SkyNet, one neighbor toward Los Angeles, and NP-CAM Grade, which carried SkyNet's advert to the Camarillo observer in one hop. [47] Ask the analyzer's maintainer to load the test names first.
  2. Instrument. On-node counters on each pilot repeater, read before and after: flood packets received and sent, duplicates, receive errors, transmit and receive airtime. [11 L28-50; 6 L232-233; 69] The analyzer is the secondary check.
  3. Configure. Tags only, using the block for each node's firmware. No default scope yet.
  4. Test 1, positive control. Send a message scoped to the pilot tag from one end of the cell. Pass: a companion at the other end, two hops away, receives it.
  5. Test 2, negative control. The same message must not be received by a companion one hop outside the cell, and the analyzer must show no path that leaves the pilot nodes. If it leaks: suspect a pre-1.10 repeater and record which one. [17]
  6. Test 3, unscoped control. An unscoped message sent in the same minute still arrives outside the cell.
  7. Test 4, the app and capitals. Type the scope in mixed case in the app and repeat Test 1. This is the case test that matters.
  8. Test 5, default scope. Set the default on one pilot node, send advert, and count the observations the analyzer records against the 64 it recorded for SkyNet's unscoped advert on 11 October. [47] Prediction: far fewer, possibly none.
  9. Test 6, direct messages. With one companion's default scope set to the pilot tag and the other unset, exchange direct messages both ways and note which acknowledgements arrive.

Inference Pilot A can prove the mechanism and expose leaks. It cannot show a load reduction, because a few test messages are invisible against roughly 6,600 floods a day. [41]

Pilot B, load, one MeshMapper zone. Recommendation Pick the zone with the best repeater coverage of its tag, set the Wardriving Scope for that zone only, and compare relays per #wardriving ping and MeshMapper coverage results for two weeks before and after. [57; 41] This is the pilot that can show the benefit, and it needs the MeshMapper administrator.

Reading the scopes already on air

Fact The firmware derives a region's key as the first 16 bytes of SHA-256 over # plus the name, and a packet's code as the first two bytes of HMAC-SHA256 under that key over one byte of payload type followed by the payload, with the values 0x0000 and 0xFFFF moved to their neighbors. [3 L175-183; 4 L4-18, L44-47] Fact The analyzer serves the raw bytes of scoped packets and marks them as scoped with no resolved name. [48; 52 L3270-3278] Fact Of 13 such packets from 11 to 13 October, 12 match a name: three flood adverts from one Coachella Valley repeater match psp; three Public messages from one user match san; four posts from a bot match california; two messages from another user match us and california. [70] Fact Twelve of the 13 came from the analyzer's latest 58 transport-route packets and one was fetched separately. [48] Calculation A single packet has about a 7 percent chance of matching some name among the 4,461 tried by accident; the same name matching three packets from one sender does not happen by accident. The lone us match is therefore probable, not certain.

Python 3, standard library only. Returns the code a packet would carry under a given name.
import hashlib, hmac

def code(name, raw_hex):
    b = bytes.fromhex(raw_hex)
    ptype = (b[0] >> 2) & 0x0F               # payload type from the header byte
    n = b[5]                                 # path length byte, after two 16-bit codes
    path = ((n >> 6) + 1) * (n & 0x3F)       # hash size times hop count
    payload = b[6 + path:]
    key = hashlib.sha256(('#' + name).encode()).digest()[:16]
    mac = hmac.new(key, bytes([ptype]) + payload, hashlib.sha256).digest()
    return mac[:2].hex().upper()             # compare with raw_hex[2:6]
